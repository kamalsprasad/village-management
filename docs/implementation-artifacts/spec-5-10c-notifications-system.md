## Intent

**Problem:** The app has no in-app notification system: no bell icon, no unread badge, no way to surface role-relevant events (at-risk learners, farm alerts, new vendors) to the users who need to act on them.

**Approach:** Add a new Appwrite `notifications` table (role-targeted, one row per event) and a `notification_reads` table (per-user read receipts), delivered exclusively through a new `createNotification` Appwrite Function that derives `target_roles` itself from a per-`type` authorization+targeting matrix (never trusts client input). Add a `notifications-store.js` Pinia store, a bell + badge + panel in `MainLayout.vue` with Appwrite realtime live updates, and wire exactly 3 triggers: at-risk learner newly flagged, farm alert newly raised, and new vendor created.

## Boundaries & Constraints

**Always:**

- The `createNotification` function derives/hardcodes `target_roles` per `type` from its own `TYPE_CONFIG`; it ignores any client-supplied `target_roles`/`target_permissions` and rejects unknown `type` values (400) and callers lacking the type's `requiredPermission` (403).
- Dedup at-risk/farm-alert notifications by querying `notifications` for an existing row with the same `type` + `related_entity_type` + `related_entity_id` before creating (crash-safe, no in-memory "last notified" state); skip (return `{success:true, skipped:true}`) if found.
- All `tables.listRows`/`functions.createExecution` calls for notifications run client-side only, guarded the same way `useGlobalSearch.js` guards Appwrite calls (`isClient`); the bell renders during SSR with count 0 and fires no queries/subscriptions.
- Realtime subscription (`Realtime` from `appwrite`, matching `useDashboardData.js`'s `tablesdb.${dbId}.tables.<id>.rows` channel pattern) is created in `onMounted` and torn down in `onBeforeUnmount`; a subscribe failure falls back to a 30s `setInterval` poll of `fetchMyNotifications` — never throws/crashes the bell.
- A failed `createNotification` call in a trigger site (at-risk, farm-alert, vendor) is caught and logged; it must never block or fail the host action (at-risk computation, alert generation, vendor creation all complete regardless).
- Quasar components only, Vue 3 `<script setup>`, hardcoded English strings, no emojis, no i18n.
- `notifications:read` granted to all 13 seeded roles (incl. via `System Administrator`'s existing `'*'`); `notifications:write` granted only to roles holding `school:read`, `farm:read`, or `vendors:write` today (Farm Manager, Crop Manager, School Administrator, Head Teacher, Teacher, Learner, Finance Manager, Village Head, Deputy Village Head) — `seed-roles.js` stays upsert-capable.

**Block If:** A new third-party dependency would be required (none identified — `Realtime`/`Permission`/`Role` are already in `appwrite`; `date-fns` `formatDistanceToNow` is already a dependency).

**Never:**

- Send email (deferred to post-MVP).
- Wire a 4th trigger, or wire into Guests/Equipment/Energy.
- Let the client set `target_roles`/`target_permissions` on a `createNotification` call and have the server trust it.
- Implement help/docs, UX/perf/mobile audit (5.10d/5.10e).

## I/O & Edge-Case Matrix

| Scenario                    | Input / State                                                                                                          | Expected Output / Behavior                                                                                                     | Error Handling                                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| User has a targeted role    | User's roles include "Farm Manager"; a `farm_alert:*` notification targets `['Farm Manager', ...]`                     | Notification appears in `fetchMyNotifications()` result and counts toward `unreadCount`                                        | No error expected                                                |
| User lacks a targeted role  | User has only "Learner"; an `at_risk_learner` notification targets `['School Administrator','Head Teacher','Teacher']` | Notification is NOT returned to this user (query-side role filter excludes it)                                                 | No error expected                                                |
| Duplicate at-risk trigger   | `computeAtRisk` re-runs after cache expiry and the same learner is still at-risk                                       | `createNotification` finds the existing `(type, related_entity_type, related_entity_id)` row and skips creation — no duplicate | Function returns `{success:true, skipped:true}`, no thrown error |
| Unauthorized create attempt | A caller without `farm:read`/`farm:write` invokes `createNotification` with `type: 'farm_alert:upcoming_harvest'`      | Function returns 403, no row created                                                                                           | Client trigger catches and logs; host action unaffected          |
| Realtime subscribe fails    | `realtime.subscribe(...)` throws (e.g. websocket blocked)                                                              | Bell falls back to 30s polling of `fetchMyNotifications`; no crash                                                             | Caught in `try/catch`, logged to console                         |
| Mark as read twice          | User clicks mark-as-read on an already-read notification                                                               | No duplicate `notification_reads` row created (existence check first); UI stays consistent                                     | No error expected                                                |
| SSR render                  | Server-side execution                                                                                                  | Bell renders with badge hidden (count 0); no `tables.listRows`, no realtime subscribe                                          | No error expected                                                |

**Acceptance Criteria:**

- Given a user whose roles include "Farm Manager", when a farm alert of a newly-raised type is generated on `FarmAlertsPage.vue`, then a `notifications` row targeting `['Farm Manager','Crop Manager','Village Head','Deputy Village Head']` is created (once) and the user's bell badge count increases within one realtime tick (or the next 30s poll if realtime is unavailable).
- Given a user whose roles do NOT include any of `['School Administrator','Head Teacher','Teacher']`, when an `at_risk_learner` notification is created, then `fetchMyNotifications()` for that user does not include it.
- Given the same at-risk learner is detected across two `computeAtRisk` cache-refresh cycles, when `notifyNewAtRiskLearners` runs both times, then only one `notifications` row exists for that learner (verified via the dedup query in `createNotification`).
- Given a caller without `vendors:write`, when `createNotification` is invoked directly with `type: 'vendor_created'`, then it returns a 403 and no row is created.
- Given the realtime subscription throws on `onMounted`, when the bell is rendered, then it still shows a (possibly stale until the next poll) count and never throws an unhandled error.
- Given SSR rendering, when `MainLayout.vue` is rendered on the server, then no `tables.listRows` call or realtime subscription occurs, and the bell renders with no badge.

(`server/functions/createNotification/src/main.js`)
  - `[low]` `[patch]` `notification_reads` table permissions and the per-row permissions set at creation were missing `delete`, inconsistent with the `file_metadata` precedent this table is explicitly modeled on. Added `Permission.delete(Role.users())` at the table level and `Permission.delete(Role.user(uid))` at row-creation time. (`server/scripts/setup-appwrite.js`, `src/stores/notifications-store.js`)

per-user `notification_reads` table (not a `read_by` array) — chosen per the epic prompt's explicit preference, and because `Query.equal('user_id', ...)` + a join-in-memory against the fetched 50 notifications is simple and avoids Appwrite array-size limits.

- **Targeting model:** `target_roles` (role NAME strings, e.g. `'Farm Manager'`, matching `authStore.userRoles[].name` and how `SYSTEM_ADMIN_ROLE_NAME`-style comparisons already work elsewhere in the codebase) is the ONLY field the store queries against for MVP. The `target_permissions` column exists in the schema (per the epic prompt's schema requirement) but is not populated or queried by any of the 3 shipped triggers — reserved for future trigger types, to keep `fetchMyNotifications` to a single query pass. This is a deliberate scope-bounding decision, not an oversight.
- **Delivery mechanism:** exclusively the `createNotification` function; the function fully ignores client-supplied `target_roles`/`target_permissions` (does not merely "validate" them) — this is the simplest way to guarantee it can't be tricked into broader targeting than its `TYPE_CONFIG` allows.
- **Dedup / "last notified" state:** derived from the `notifications` table itself (existence query keyed on `type`+`related_entity_type`+`related_entity_id`), not from any in-memory set in the Pinia stores — crash-safe across page reloads and multiple browser tabs, per the epic prompt's explicit recommendation.
- **Farm alert type namespacing:** `generateFarmAlerts()` produces `alert_type` values (`upcoming_harvest`, `overdue_harvest`, `low_inventory`, `underperforming_yield`, `crop_failure`) that are NOT unique combined with `related_entity_type` alone (a planting could have two different alert types simultaneously), so the notification `type` column is set to `farm_alert:<alert_type>` — this makes the 3-column dedup key (`type`, `related_entity_type`, `related_entity_id`) unambiguous without adding a 4th schema column.
- **Table permission model:** `notifications` grants `read` to `Role.users()` only (no client `create`/`update`/`delete` — the function's admin API key bypasses table permissions entirely, so client roles never need write access). `notification_reads` uses `rowSecurity: true` with per-row `Permission.read/update(Role.user(userId))` set at creation, exactly like the existing `file_metadata` table — this avoids extending the platform-wide `"any"` permission debt already logged in `deferred-work.md` for a brand-new table where it's easy to avoid.
- **Bell placement:** placed just before the user-menu `q-btn`, OUTSIDE the `class="gt-xs"` search wrapper, so it (unlike the search box) stays visible at `xs`. The badge is a `q-badge floating` on the bell, not a separate element, so it doesn't consume extra header width.
