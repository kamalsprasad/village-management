## Executive Summary

Epic 5 closed out the MVP by delivering the village calendar, role-based cloud
storage (personal + shared), the Vendors module, module management, the full
system-completion suite (dashboard wiring, navigation polish, notifications,
UX/accessibility, performance, mobile responsiveness, help/docs, final testing
checklist), the Start Fresh production setup wizard, user management CRUD,
role assignment UI, and auth completeness (password change/reset).

All 11 MVP stories are marked `done` in `docs/sprint-status.yaml`. There is no
Epic 6 — Epic 5 is the final MVP epic. Post-MVP work is tracked in
`docs/POST-MVP.md` and `docs/implementation-artifacts/deferred-work.md`.

**Headline finding:** Epic 5 delivered the MVP, but the project has a systemic
habit of identifying the same architectural debts in every retro and code
review, deferring them to "post-MVP" or "the next story," and never closing
them. The clearest evidence: the #1 critical security action item from the
Epic 3 retrospective — a 5-minute fix to `FarmIndexPage.vue` — was still live
in the codebase at the start of this retro, two epics later. It was fixed
during this retrospective session.

**User decision on release posture:** Single-tenant, trusted-user deployment is
acceptable now. Multi-user/multi-village hardening (server-side row security,
pagination, etc.) is post-MVP. See Critical Path.

## What Went Well

1. **The full MVP shipped.** Calendar, storage (personal + shared with per-file
   security), vendors, module management, production wizard, user management,
   role UI, auth completeness, notifications, nav polish, and the
   UX/perf/mobile/testing pass all landed.

2. **`deferred-work.md` is high-quality process hygiene.** Every code-review
   finding is logged with `source_spec`, `summary`, `evidence`, and
   `owning_story`. This is the single best artifact the project produces and
   should be kept as a permanent practice.

3. **`bmad-dev-auto` guardrails worked.** The loop correctly HALTED on the
   unapproved `vue-i18n@9` dependency (Story 5.1) and on a dirty working tree
   (Story 5.7) rather than silently proceeding. This is the discipline working
   as designed.

4. **Cross-module pattern reuse.** The dashboard widget pattern, three-way
   integration pattern, and sample-data seeding pattern from Epics 2–3 were
   reused in Epic 5 (vendors widget, vendor→finance/farm integration, vendor
   seed data).

5. **Per-row security was applied where it mattered most.** `file_metadata`
   (owner-only RUD) and `personal_files` bucket (per-user file permissions)
   got real row-level security in 5.3/5.4 — the first tables in the codebase
   to do so. This is a positive precedent.

6. **Story splitting, once triggered, was disciplined.** When 5.10 proved too
   broad, it was split into 5.10a–e with `sprint-status.yaml` kept in sync;
   when 5.10e proved too broad, it was split into e1–e4. The tracking was
   clean even though the original sizing was not.

7. **`final-testing-checklist.md` (§9a–9i) is a thorough manual MVP sign-off
   document** covering user journeys by module, RBAC matrix, data-integrity
   invariants, integration smoke tests, sample-data lifecycle, mobile 320px,
   performance/3G, the AC8 deferral expansion, and the post-MVP testing epic.

8. **Last-System-Administrator guard was added.** Story 5.11 added the
   missing guard to `updateUser` (role removal) mirroring the pre-existing
   `deactivateUser` guard — closing a lockout vector surfaced by 5.13.

## Problems Identified, with Solutions and Recommendation

### 🔴 P1. Retrospective action items are not followed through (process failure)

**Problem:** 0/6 Epic 3 action items were closed before this session. Epic 4's
retro was skipped. The team identifies the same debts every cycle and defers
them into a black hole.

**Solutions:**
- (A) Enforce the workflow's existing "previous retro action items" review as
  the **first** agenda item of every retro, with explicit ✅/❌ tracking.
- (B) Cap deferrals: any debt deferred more than once auto-escalates to a
  mandatory hardening sprint before the next epic begins.
- (C) Track action items in `sprint-status.yaml` (not just markdown) so they
  surface at sprint planning.

**Recommendation: A + B.** The workflow already specifies A; the missing
piece is B — a rule that repeat-deferred items force a hardening sprint. This
is the single most important change from this retro.

---

### 🔴 P2. Server-side row-level security not enforced (platform-wide)

**Problem:** `server/scripts/setup-appwrite.js:114` applies
`read/create/update/delete("any")` to **26 tables**. Any authenticated user
can read/write all rows regardless of role. Only `file_metadata` and
`personal_files` have per-row security. The `TODO` has been present since
Epic 1 and was re-hit by every Epic 5 story that added a table (vendors,
village_events, notification_reads).

**Solutions:**
- (A) Per-table row security via Appwrite per-row permissions on each CUD call
  (high effort, touches every store).
- (B) Move CUD operations behind server-side Appwrite Functions that verify
  role + ownership before writing (medium effort, centralizes enforcement;
  pattern already exists for User Management + storageUsageReport).
- (C) Accept for single-tenant MVP; ship a hardening sprint before any
  multi-village/multi-user deployment.

**Recommendation: B, as the first post-MVP hardening story.** Functions are
already in use so the pattern exists. **Do not deploy to a real multi-user
village until this is done** (per user decision, single-tenant trusted-user
deployment is acceptable now).

---

### 🔴 P3. Epic 3 security fix was still live (CLOSED this retro)

**Problem:** `src/modules/farm/pages/FarmIndexPage.vue:104` was
`return true; // TODO: Implement proper role check` — all users saw Farm
Manager actions regardless of role.

**Resolution:** Fixed during this retro to
`const hasFarmManagerRole = computed(() => hasPermission('farm:write'));`
using `usePermissions()` (the established codebase pattern). ESLint passes.
A codebase sweep for `return true; // TODO` found no other instances.

**Recommendation: Closed.** Carry forward as a lesson (P1) about why it
survived two epics.

---

### 🟡 P4. Systemic unbounded `Query.limit()` with no pagination

**Problem:** **102 `Query.limit()` calls across 32 files**, every list store
capped at 200–500 rows with no cursor pagination. Beyond the cap, newer rows
**silently never load** (oldest kept due to `orderAsc`). Epic 5 added more
(calendar 500, personal_files 500, vendors 200, vendor history 100/side,
users 500).

**Solutions:**
- (A) Build a shared `fetchAllPaginated()` helper using `Query.cursorAfter()`
  and refactor every capped store.
- (B) Add the helper + migrate the highest-risk stores first (calendar_events,
  personal_files, users, vendors); rest in post-MVP.
- (C) Leave as-is; villages are small (50–1000 people).

**Recommendation: B now, A as the post-MVP pagination pass.** At 50 adults the
cap is fine, but the roadmap targets 1,000 by year 30 and recurring calendar
events accumulate fast. Silent data loss is worse than slow pagination.

---

### 🟡 P5. `seed-roles.js` skips existing roles — new permissions silently miss existing deployments

**Problem:** The seeder `continue`s on existing roles. Epic 5 hit this **four
times** (5.2 `calendar:write`, 5.3 `storage:*`, 5.4 shared-storage grants, 5.7
`vendors:*`). Each was deferred to "Story 5.13 or an ops runbook." Story 5.13
is a read-only roles UI and **does not fix the seeder**. No upsert migration
exists.

**Solutions:**
- (A) Change `seed-roles.js` to upsert (update permissions/quotas on existing
  roles instead of skipping).
- (B) Write a one-time `migrate-role-permissions.js` for existing deployments.
- (C) Document manual Appwrite-console steps in an ops runbook.

**Recommendation: A + B.** The seeder skip was explicitly forbidden to change
by the 5.2 spec, but that constraint is now actively harming every deployment.
An upsert seeder + migration script closes this permanently. C alone is not
acceptable — it has been the default for four stories and never got done.

---

### 🟡 P6. Zero automated test infrastructure

**Problem:** `package.json` `test` is `echo "No test specified" && exit 0`.
No Vitest/Cypress/Playwright. No `*.test.js` files. MVP sign-off relies on the
manual `final-testing-checklist.md`. Flagged in Epic 3 retro; deferred again
in Epic 5.

**Solutions:**
- (A) Run the planned post-MVP testing epic (XL) — Vitest unit + store + E2E.
- (B) Minimal first story (L): Vitest + CI wiring + unit tests for the 5
  highest-risk pure functions (`permissions.js`, `at-risk-utils.js`,
  `school-utils.js`, `module-registry.js`, `format-storage.js`).
- (C) Accept manual-only for MVP.

**Recommendation: B as the very first post-MVP story.** Full XL is too big to
land in one go; a minimal L-story establishes the harness + CI so future tests
are trivial to add. The manual checklist is fine for MVP *release* but not for
*ongoing changes*.

---

### 🟡 P7. Story 5.10 was under-sized as a single story (8 sub-stories)

**Problem:** 5.10 had 8 ACs spanning dashboard, nav, notifications, UX,
performance, mobile, help, system health, testing. It was split into 5.10a–e,
then 5.10e into e1–e4 = 8 sub-stories. Repeated splitting signals stories
weren't right-sized at planning.

**Solutions:**
- (A) Adopt a "one concern per story" rule at epic planning — if an AC spans
  an independently shippable concern, it's its own story from the start.
- (B) Planning gate: any story with >5 ACs gets pre-split before
  `sprint-status.yaml` entry.

**Recommendation: A + B.** The splitting was handled well *once it started*,
but it cost re-planning overhead. Catching it at planning is cheaper.

---

### 🟢 P8. Smaller live concerns (documented, lower priority)

- **i18n deferred** — all UI hardcoded English (PRD NFR-4 / architecture §12
  unmet). Accepted user decision (2026-07-28). Fine for MVP Zambia deployment;
  blocks any non-English rollout. Owning story: post-MVP i18n epic.
- **`/setup` route not RBAC-gated** — any authenticated user can launch the
  Start Fresh wizard. Pre-existing from original `SetupWizard.vue`. Owning
  story: post-MVP RBAC hardening.
- **TOCTOU race on last-admin guard** (5.11 + pre-existing `deactivateUser`)
  — two concurrent role-removal requests against the last two admins could
  both pass the count check. Low probability. Owning story: post-MVP
  concurrency hardening.
- **Realtime subscribe only catches sync throws** — async websocket failure
  leaves no polling fallback (notifications bell + finance dashboard). Systemic
  pattern. Owning story: post-MVP realtime hardening (fix both consumers
  together).
- **`bg-info text-white` fails WCAG AA contrast** (~1.8:1 vs 4.5:1) across
  10+ files — 5.10e1 flagged but too high blast-radius to fix without a
  re-theme decision. Owning story: post-MVP theming pass.
- **Spec drift:** `resetUserPassword` added to 5.12 after spec marked done
  (commit `f47fc6c`); audit enum went 4→5 values. Accepted (user decision
  2026-08-04), but the 5.12 spec is now out of sync with code.
- **Config/path mismatch:** `_bmad/bmm/config.yaml` says
  `planning_artifacts: docs/planning-artifacts`, but `epics.md` and
  `sprint-status.yaml` live at `docs/` root and retrospectives live in
  `docs/sprint-artifacts/`. The retrospective workflow's path resolution
  silently fell back. Worth fixing so future skills don't break.
- **`notification_reads` table-level `create("any")`** — a user could craft a
  direct API call marking another user's notification read. Low-impact
  griefing vector; same trust model as `file_metadata`. Owning story:
  post-MVP security hardening.
- **`country_phone_code` maxLength 4** rejects valid codes >4 chars (e.g.
  `+1242`). Pre-existing, surfaced by 5.11. Owning story: post-MVP
  i18n/localization.
- **`User Management` function directory has a space** — friction-prone for
  `appwrite push function` and shell scripts. Owning story: post-MVP rename
  (alongside `Check Users Exist`).

## Key Takeaways

1. **Retrospectives that don't drive follow-through are theater.** 0/6 Epic 3
   action items were closed before this session. The process must enforce
   accountability (P1).
2. **The same four debts appear in every cycle** — server-side security,
   pagination, test coverage, error logging. They will keep appearing until a
   hardening sprint actually closes them.
3. **Epic 5 itself was well-executed operationally** — strong review hygiene
   (`deferred-work.md`), working guardrails (`bmad-dev-auto` halts),
   disciplined story splitting, and the full MVP shipped.
4. **Single-tenant MVP is deployable now; multi-user is not.** The security
   and pagination debt is acceptable for one trusted village and unacceptable
   for many.
